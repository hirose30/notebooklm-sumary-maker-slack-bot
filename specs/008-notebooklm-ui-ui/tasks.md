# タスク: NotebookLM UI バージョンサポート (旧UI・新UI互換性)

**入力**: `/specs/008-notebooklm-ui-ui/` の設計ドキュメント
**前提条件**: plan.md (必須), spec.md (ユーザーストーリー用必須), research.md, data-model.md, contracts/

**テスト**: この機能では明示的なテスト要求がないため、テストタスクは含まれていません。実装後に手動での統合テストを推奨します。

**構成**: タスクはユーザーストーリーごとにグループ化され、各ストーリーを独立して実装・テスト可能にしています。

**⚠️ 重要な環境情報**:
- **ws1**: 新UI環境（NotebookLMアカウントが新UIに移行済み）
- **ws2**: 旧UI環境（既存環境、NotebookLMアカウントが旧UIのまま）
- このため、新UIの調査はws1で、旧UIの調査はws2で実施する必要があります

## 依存関係と実行順序

### フェーズの依存関係

- **セットアップ（フェーズ1）**: 依存関係なし - すぐに開始可能
- **基盤（フェーズ2）**: セットアップ完了後 - すべてのユーザーストーリーをブロック
- **ユーザーストーリー（フェーズ3+）**: すべて基盤フェーズ完了後
  - **US4（DOM調査）**: 最優先（US1とUS2の実装前に必要）
  - **US1（旧UI）**: US4完了後に開始可能
  - **US2（新UI）**: US4完了後に開始可能（US1と並行可能）
  - **US3（設定移行）**: US1とUS2の両方完了後
- **ポリッシュ（最終フェーズ）**: すべての望ましいユーザーストーリー完了後

### ユーザーストーリーの依存関係

```
基盤（フェーズ2完了）
    ↓
US4（DOM調査）← 最優先
    ↓
    ├→ US1（旧UI）← MVP候補
    └→ US2（新UI）← US1と並行可能
        ↓
    US3（設定移行）← US1とUS2の両方が必要
```

### 各ユーザーストーリー内

- モデル → サービス → 統合
- コア実装 → エラーハンドリング
- 実装 → 手動テスト
- 次の優先度に移行前にストーリーを完成

### 並行実行の機会

- セットアップの全タスク [P] マークは並行実行可能
- 基盤フェーズの [P] マークタスクは並行実行可能
- US1とUS2は、US4完了後に並行作業可能（チーム人員が許せば）
- 同じストーリー内の [P] マークタスク（異なるファイル）は並行実行可能

## 実装戦略

### MVP優先（ユーザーストーリー1のみ）

1. フェーズ1完了: セットアップ
2. フェーズ2完了: 基盤（重要 - すべてのストーリーをブロック）
3. フェーズ3完了: US4（DOM調査）
4. フェーズ4完了: US1（旧UI）
5. **停止して検証**: US1を独立してテスト
6. 準備できたらデプロイ/デモ

### 段階的デリバリー

1. セットアップ + 基盤完了 → 基盤準備完了
2. US4追加（DOM調査） → ドキュメント化完了
3. US1追加（旧UI） → 独立してテスト → デプロイ/デモ（MVP!）
4. US2追加（新UI） → 独立してテスト → デプロイ/デモ
5. US3追加（設定移行） → 独立してテスト → デプロイ/デモ
6. 各ストーリーが前のストーリーを壊さずに価値を追加

### 並行チーム戦略

複数の開発者がいる場合:

1. チーム全体でセットアップ + 基盤を完了
2. 基盤完了後:
   - 開発者A: US4（DOM調査）
   - US4完了後:
     - 開発者A: US1（旧UI）
     - 開発者B: US2（新UI）
   - US1とUS2完了後:
     - 開発者A or B: US3（設定移行）
3. ストーリーが完了し、独立して統合
